# SlotBook: план разработки с Astra

Дата: 24 октября 2026. Основа: [архитектура, редакция 3](slotbook-architecture.md). Добавлены ветки, pull requests и релизы.

Статус: подготовлен план. Этапы реализации не запускались; тесты приложения и сборки ещё не выполнялись. Существующий interview-tracker не является реализацией SlotBook.

## 1. Как работаем

Пользователь хочет сначала получить полностью работающий проект с помощью Codex, затем разобраться в его устройстве. Агент пишет файлы, запускает проверки, исправляет ошибки и документирует результат. Пользователю не нужно вручную переносить код из ответов в редактор. Учебный разбор выделяется в самостоятельный этап после готовой версии.

Новый проект создаётся в slotbook/ внутри текущего рабочего каталога. sources/ остаётся только для чтения; interview-tracker и другие существующие проекты не меняются.

Этап — законченный небольшой результат с критериями готовности. Если он не помещается в один проход, допустимы 2–3 подзадачи с сохранением прогресса. Число сообщений модели не является критерием завершения.

Порядок: прочитать текущие файлы → реализовать один этап → выполнить его проверки → исправить выявленное → обновить фактический статус → перейти к следующему выбранному этапу. Сначала этапы 01–12 дают законченный MVP. Затем 13–15 доводят проект до Backend + AI. Внешние аккаунты и доступы запрашиваются только когда реально нужны; до этого используются локальные проверяемые адаптеры и тестовый провайдер уведомлений.

## 2. Модель и усилие

Основная модель по пожеланию пользователя — GPT-6 Astra. Рекомендации ниже — инженерный выбор для этого проекта, а не результат сравнительного теста моделей:

- medium: каркас, UI по утверждённому стилю, небольшие изменения и учебные объяснения.
- high: проектирование связей, транзакции, авторизация, frontend/backend интеграция, Docker/CI и содержательный review. Это основной режим для наиболее связанных частей проекта.
- xhigh: трудновоспроизводимая гонка, сложная ошибка интеграции или неясный дефект безопасности, если high не дал проверенного решения. Сначала собрать воспроизведение и факты.
- max: в исходном плане не нужен. Повышение усилия оправдывается улучшением результата на конкретной проблеме.
- low: только механические правки текста/оформления после согласованного решения.

Выбор модели/усилия выполняется в доступных настройках Codex. Фраза «работай как Astra high» в сообщении сама по себе не переключает выбранную модель. Этот план также не меняет настройки чата автоматически.

Официальная основа: [OpenAI: выбор reasoning effort](https://developers.openai.com/api/docs/guides/deployment-checklist), [reasoning models](https://developers.openai.com/api/docs/guides/reasoning). Повышенный effort может увеличивать расход reasoning tokens и задержку; конкретный выигрыш на SlotBook заранее не измерен. Практика постановки: [в запросе задавать поведение, контекст, ограничения и проверку](https://learn.chatgpt.com/docs/prompting).

## 3. Общие правила для каждого этапа

1. Архитектура и контракт API — общая основа frontend/backend. При необходимости изменить контракт сначала обновить его и потребителей в рамках одного этапа.
2. Код ограничен задачей этапа. Массовые переписывания соседних модулей допустимы только при доказанной необходимости.
3. Production код не подменяется mock-данными. Тестовые заглушки разрешены в тестах; временный UI-preview помечается явно и удаляется из рабочего пути до завершения этапа.
4. Бизнес-правила бронирования обеспечиваются backend и PostgreSQL. Frontend проверяет ввод и понятно показывает ошибки.
5. Выполняются проверки, соответствующие риску изменения. Не надо тестировать каждую CSS-строку; надо проверять реальные сценарии, права и гонки.
6. «Готово» означает выполненные критерии, а не просто созданные файлы. Если PostgreSQL/Docker/браузер недоступны, отчёт прямо разделяет выполненное и непроверенное. Невыполненные проверки не засчитываются.
7. После этапа обновляется журнал с командами, итогами, известными ограничениями и следующим действием. Секреты и личные данные в журнал не попадают.
8. Работа ведётся последовательно в одном checkout. Отдельные чаты, параллельные агенты и публикация во внешние системы не запускаются этим документом автоматически.

## 4. Карточки реализации

### Правила Git для всех карточек

Схема: стабильная main → короткая ветка этапа → проверки и review → pull request → squash merge в main. Постоянная develop для этого последовательного solo-проекта не требуется. Законченное проверенное приложение в итоге находится в main; текущая работа и эксперименты ведутся в отдельных ветках.

Перед этапом 01 проверить, является ли slotbook/ частью существующего Git-репозитория. Если нет — создать отдельный репозиторий внутри slotbook/, не превращая всю папку зеркала ChatGPT в репозиторий приложения. Если подходящий репозиторий уже существует — сохранить его историю и remotes. Разрешён минимальный начальный commit README/.gitignore в main, чтобы появилась база для первой feature-ветки; реализация начинается уже в ветке этапа.

Имена веток описывают задачу и не содержат номер этапа. Номера сохраняются в плане, описании PR и журнале прогресса:

| Тип работы | Пример |
|---|---|
| Этап 01 | feat/project-foundation |
| Этап 02 | feat/database-migrations |
| Этап 03 | feat/read-api-contract |
| Этап 04 | feat/public-react-page |
| Этап 05 | feat/booking-transactions |
| Этап 06 | feat/client-booking-flow |
| Этап 07 | feat/owner-auth-api |
| Этап 08 | feat/owner-dashboard |
| Этап 09 | test/browser-scenarios |
| Этап 10 | chore/production-ci |
| Этап 11 | fix/review-findings |
| Этап 12 | docs/mvp-release-guide |
| Этап 13 | feat/redis-rate-limits |
| Этап 14 | feat/background-notifications |
| Этап 15 | feat/ai-slot-search |
| Исправление | fix/booking-cancellation-race |
| Документация | docs/architecture-walkthrough |
| CI и инструменты | chore/ci-pipeline |
| Учебный эксперимент | learn/booking-transaction |

Один этап — обычно один PR; большой этап допускает несколько последовательных небольших PR с самостоятельной проверкой. Следующий этап начинается от main после интеграции предыдущего. Незавершённую ветку сохранять для продолжения; не создавать новую копию той же задачи и не переносить незакоммиченные изменения между задачами молча.

Этапы не получают ветку заранее: она создаётся при начале работы. Для этапа 11 ветка fix/* создаётся только при фактических исправлениях; если review не обнаружил проблем, его результат фиксируется в журнале без пустого PR. Этапы 09 и 12 также могут включать небольшие исправления, необходимые для их критериев готовности.

Пример последовательности:

```text
main → feat/project-foundation → PR + проверки → main
main → feat/database-migrations → PR + проверки → main
main → feat/read-api-contract → PR + проверки → main
...
main после этапа 12 → проверка релиза → tag v0.1.0
```

В main постепенно собирается готовое приложение, а история этапов остаётся в PR, squash-коммитах и тегах. Удаление уже объединённой ветки не удаляет эту историю. Для чтения состояния прошлого релиза используется его tag; для учебных изменений создаётся learn/* от нужного commit. Постоянно держать 15 устаревших веток ради сохранности кода не требуется.

Перед изменениями проверять текущую ветку и рабочее дерево. Не стирать чужие изменения, не применять reset --hard и не делать force push в общие ветки. Коммиты небольшие и осмысленные: feat(slots): add availability filtering; fix(bookings): serialize cancellation; test(bookings): cover concurrent requests. Секреты, .env, node_modules, .venv, сборки и дампы БД исключены из истории; lock-файлы и миграции включены.

PR содержит задачу/номер этапа, изменение поведения, фактические проверки и известные ограничения; для UI — скриншоты. Проверки привязаны к последнему commit PR. Созданный PR прикрепляется к текущему чату. Пока GitHub remote не подключён, этап получает локальную feature-ветку, коммиты и готовое описание PR; наличие PR, remote CI и branch protection не заявляется. Подключение remote и публикация выполняются, когда пользователь поручит работать с конкретным репозиторием.

В GitHub целевые настройки main: обязательный PR, обязательные checks, запрет удаления и force push. Имена required checks задаются после первого реального прогона; до этапа 10 действуют выполненные локальные проверки, затем полноценный CI. Доступность правил зависит от репозитория/тарифа. В одиночной разработке не требовать формального одобрения вторым человеком, которого нет: выполнять отдельный review-проход, а обязательные CI checks сохранять. Настроенная защита и просто описанная защита — разные статусы. Основание: [GitHub protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).

После проверки изменений и при наличии поручения на интеграцию — squash merge. Ветка может удаляться после подтверждённого merge: история изменения сохраняется в main, PR и релизных тегах. Если этап только реализован, а PR не интегрирован, журнал явно отмечает «реализован в ветке / ожидает интеграции», а не «доступен в main».

Релизные теги ставятся на проверенные commits main: v0.1.0 — MVP после 12; v0.2.0 — Redis; v0.3.0 — очереди/уведомления; v0.4.0 — AI. Исправления выпускаются как v0.1.1 и далее. Это целевые версии, пока они не созданы. Версия приложения едина для frontend/backend и фиксируется при релизе в pyproject.toml, package.json/lock и CHANGELOG.md. Docker-образ также маркируется commit SHA; деплой ссылается на определённый релиз, а не на плавающий latest. Версия API /api/v1 — отдельный контракт, она не обязана меняться с каждым релизом приложения.

Применённые миграции не переписываются в последующих PR: изменение БД получает новую ревизию Alembic. Откат кода не означает автоматический откат данных; перед релизом проверяются совместимость схемы и способ восстановления. Учебные поломки из раздела 6 выполняются в learn/* и не сливаются в main.

Журнал каждого этапа дополнительно содержит ветку, commit SHA, ссылку/статус PR при его наличии, результаты проверок и статус интеграции. Реальное создание репозитория, веток и правил защиты начинается при реализации; данное изменение добавляет только правила в план.

Сделать: создать slotbook/backend и slotbook/frontend; Python/FastAPI/settings/logging, React/TypeScript/Vite, uv/npm lock-файлы, .env.example, .gitignore, базовые команды, Vite proxy. Проверить локальные версии Python/Node/Docker до установки; несовместимость среды описать и использовать доступный подходящий runtime.

Готово: обе части запускаются по README, React отображает доступность API; backend smoke test, tsc и frontend build проходят. Секретов в VITE_* нет. Здесь пока не создаются фиктивные booking endpoints и полноценный кабинет.

### 02 — БД, миграции и демонстрационные данные

Модель: Astra high. Зависимости: 01.

Сделать: PostgreSQL Compose, SQLAlchemy models, sessions, Alembic; таблицы users/sessions/specialists/slots/bookings; частичный UNIQUE и exclusion constraint; явный идемпотентный seed с синтетическими данными. Установить корректные FK, NOT NULL, CHECK и значения статусов. Seed создаёт будущие слоты относительно даты запуска.

Готово: upgrade работает на пустом PostgreSQL; downgrade/upgrade проверены только в одноразовой тестовой БД; повторный seed не создаёт дубликаты; тесты ограничений запрещают пересечения и две confirmed-записи на один слот. Строки Asia/Omsk и timestamps хранятся согласно архитектуре.

Тест 20 конкурентных запросов с отдельными соединениями даёт ровно один 201. Остальные получают ожидаемый 409, а не случайные 500. Время проверяется после блокировки. Готово: у каждого обнаруженного дефекта есть воспроизведение, исправление и соответствующая проверка. Нет открытых критических проблем; оставшиеся ограничения описаны. Полный прогон выполняется после содержательных исправлений. Review в отдельном проходе полезен, но не даёт гарантии независимости, если его делает та же модель.

### 12 — Готовый MVP и материалы для изучения

Модель: Astra medium, проверка финального релиза high. Зависимости: 11.

Сделать: README с запуском и примерами API, ER/схема потока запроса, синтетическое демо, сценарий демонстрации за 2–3 минуты, release checklist. Подготовить docs/walkthrough.md на основе фактических файлов и docs/learning-path.md. При доступном целевом сервере подготовить и проверить деплой; при его отсутствии честно отметить отсутствие публичного URL. Внешняя публикация не считается выполненной по одному Docker build.

Готово: проверенный локальный production MVP; итоговые команды и ограничения записаны. Учебный разбор ссылается на реальные файлы, а не на придуманную структуру. Пользователь может запустить сценарий и получить объяснение любого перехода frontend → API → DB → response.

### 13 — Redis и общий rate limit

Модель: Astra high. Зависимости: 12.

Сделать: Redis Compose, атомарные лимиты входа и публичной записи, 429/Retry-After, тесты и документированное поведение при недоступности Redis. Для login при сбое прикладного лимитера использовать явное ограничивающее поведение; не скрывать деградацию. Публичная доступность слотов не кэшируется в MVP.

Готово: несколько процессов API соблюдают общий лимит; сбой Redis покрыт тестом; схема бронирования продолжает полагаться на PostgreSQL. CI/документация/Compose обновлены и проверены.

### 14 — Уведомления через Celery/RabbitMQ и внешний API

Модель: Astra high. Зависимости: 13.

Сделать: outbox, dispatcher, Celery worker, durable RabbitMQ queue, email client HTTPX, timeouts/retry/backoff, статусы доставки. Локальный тестовый провайдер позволяет проверять проект без платного аккаунта. Реальный провайдер подключается через тот же интерфейс с настоящими credentials, когда они доступны.

Готово: booking и event атомарны; сбой брокера не теряет событие; повтор event_id проверен; подтверждена заявленная at-least-once семантика и описана возможность дублирования письма без provider idempotency. Тесты 429/5xx/timeout выполняются локально; реальная доставка не заявляется без её проверки. Обновлены UI-статусы при необходимости, CI, Compose и учебные материалы.

### 15 — AI-подбор времени и оценка качества

Модель разработчика: Astra high. Модель внутри продукта выбирается отдельно по latency/цене/качеству, Astra для неё не обязательна. Зависимости: 14.

Сделать: LLMClient, structured output → Pydantic, нормализация пожеланий по текущей дате/timezone, вызов read-only поиска, уточнение неоднозначного ввода. Небольшой React-диалог с показом реальных слотов и явным подтверждением. Добавить eval-набор 20–30 случаев, timeout/fallback и лимит расходов. Сначала проверить доступный способ подключения модели и credentials.

Готово: AI не создаёт запись без подтверждения и не придумывает свободные слоты; невалидный ответ/неоднозначность/сбой дают понятный результат. Eval запускается воспроизводимо, фактические результаты записаны; нет выдуманной accuracy. Если ключа нет, завершены только локальные части, а live-интеграция остаётся открытой. Финальный релиз и walkthrough обновлены после полного прогона. RAG/LangGraph добавляются отдельным согласованным расширением при наличии реальной потребности.

## 6. Как будем разбирать проект после сборки

1. Пользовательский сценарий и карта каталогов: что запускается и где искать каждую функцию.
2. Один сквозной запрос: React form → fetch → Pydantic → service → repository → SQL → response → query invalidation.
3. PostgreSQL: ER, ограничения, миграции, индексы, блокировки и доказательство конкурентного поведения.
4. Авторизация: cookie, session hash, CSRF, ownership и клиентская секретная ссылка.
5. React: routing, local state, server state, формы, ошибки и cache.
6. Тесты: запустить проверку, прочитать её смысл, намеренно сломать отдельную гарантию в учебной ветке и увидеть отказ теста.
7. Docker/CI/deploy: путь запроса через Nginx и диагностика отказа сервиса.
8. Расширения: outbox, повторная доставка, LLM-валидация и eval.

Формат каждой учебной сессии: короткая схема → конкретный код → одно упражнение → проверка понимания. Сначала разбор реально работающего сценария, затем термины и варианты архитектуры. Не требуется одновременно учить весь React и весь backend.
