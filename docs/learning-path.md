# Как изучать проект

Используйте [разбор запроса](walkthrough.md) как карту. Для эксперимента создайте
ветку `learn/booking-flow` от `main` и локальную БД с демо-данными. Учебные поломки
не нужно отправлять в `main`; не экспериментируйте с рабочими контактами клиентов.

| Тема | Что открыть и сделать | Вопрос для самопроверки |
|---|---|---|
| Путь запроса | BookingForm → api.ts → bookings/router.py → service.py; проследить Network в браузере | Чем ответ 201 отличается от завершённого flush? |
| Модель данных | models.py, миграции, tests/integration/test_database.py | Почему cancelled-записи не мешают новой записи на тот же слот? |
| Конкурентность | repository.py и `test_twenty_concurrent_tcp_requests_one_booking` | Что произойдёт без блокировки? Какую гарантию всё равно даст индекс? |
| Авторизация | owner/dependencies.py, test_owner.py, manage-token.ts | Почему UUID записи недостаточно для доступа? Чем Bearer отличается от cookie+CSRF? |
| Даты | dates.ts, owner-dates.ts и их Vitest-тесты | Почему календарный день не всегда равен 24 часам? |
| Состояние React | query-client.ts, owner-session.ts, pages/manage.tsx | Почему нельзя автоматически повторять POST после timeout? |
| Контракт | schemas.py → docs/openapi.json → generated/api-types.ts | Что ломается в CI, если поменять Pydantic без генерации типов? |
| Эксплуатация | compose.production.yaml, nginx.conf, scripts/check-production.sh | Чем liveness отличается от readiness при остановленной БД? |

Пути выше ищите в `backend/app/`, `backend/tests/` и `frontend/src/`;
точные ссылки собраны в [walkthrough](walkthrough.md).

Практика: в учебной ветке измените текст ошибки занятого слота и проследите,
как он проходит через API. Затем добавьте локальную проверку граничного времени
в существующий тест дат. Для экспериментов с ограничениями БД используйте только
случайную БД тестовой fixture; применённую миграцию рабочего проекта не переписывайте.

Команды для узких проверок (из корня):

```bash
make db-up db-test
cd frontend && npm run test:unit -- src/lib/dates.test.ts
```

Для полного прогона вернитесь в корень и следуйте разделу проверок в README.
Перед объяснением результата ответьте: где проверяется правило, кто владеет
транзакцией, какой тест отличит корректное поведение от случайного успеха?
