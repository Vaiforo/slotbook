# Выпуск и эксплуатация

Версия приложения одинакова в `backend/app/__init__.py`, pyproject/uv.lock,
frontend package/lock и OpenAPI. `make version-check` проверяет совпадение и запись
в [CHANGELOG](../CHANGELOG.md). Версия `/api/v1` — отдельный контракт, её не нужно
менять при каждом выпуске приложения.

## Проверка перед выпуском

Это повторяемый список действий для выпуска, а не журнал выполненных работ.

- [ ] Прочитать CHANGELOG и проверить чистое рабочее дерево.
- [ ] Выполнить полный прогон с PostgreSQL и Chromium:

  ```bash
  make install db-up
  SLOTBOOK_TEST_ADMIN_URL=postgresql+psycopg://slotbook:slotbook_local_only@127.0.0.1:5432/slotbook make check
  cd frontend && npx playwright install chromium && cd ..
  make smoke
  bash scripts/check-production.sh
  ```

- [ ] Пройти [демо](demo.md). Убедиться, что нет настоящих контактов в данных показа.
- [ ] Дождаться успешных `checks` и `containers` у последнего commit PR.
- [ ] Слить PR и поставить тег `v<версия>` на соответствующий commit `main`.
  Тег не переносить: исправление получает новую версию.
- [ ] Для развёртывания выбрать этот commit, создать `.env.production`, собрать
  образы с `IMAGE_TAG`, равным SHA, и выполнить команды Docker из README.

Production-проверка создаёт пустую БД, применяет миграции, запускает синтетическое
бронирование/отмену через Nginx и восстанавливает дамп в отдельную БД. Также она
проверяет маршруты SPA, контракты ошибок и восстановление API/БД после сбоя.
При ошибке прогон завершается с ненулевым кодом; оставшиеся проверки не считаются выполненными.

## HTTPS и данные на сервере

Комплект содержит локальную production-сборку, но не публичный адрес или сертификаты.
На целевом сервере нужны TLS termination перед loopback-портом Nginx, точный
`SLOTBOOK_PUBLIC_ORIGIN`, защищённый env-файл и место для резервных копий. Проверьте
Secure cookie через HTTPS, вход/выход и демо без реальных контактов после установки.
Порт БД наружу не открывайте. Лимит Nginx использует адрес подключившегося клиента;
за внешним proxy настройка доверенных адресов зависит от конкретной инфраструктуры.

`docker compose down` сохраняет volume. Не применяйте `down -v` к рабочему проекту:
это удаляет БД. Смена POSTGRES_PASSWORD в env не меняет пароль существующей БД.
Дамп содержит контакты, хеши токенов и сессий — защищайте его как рабочие данные.

## Резервная копия и пробное восстановление

Команды ниже для Bash из корня проекта. Они не заменяют расписание резервного
копирования, хранение копий вне сервера и правила доступа к ним.

```bash
(
set -euo pipefail
compose=(docker compose --env-file .env.production -f compose.production.yaml)
umask 077
mkdir -p .local/backups
backup_file=".local/backups/slotbook-$(date -u +%Y%m%dT%H%M%SZ).dump"
"${compose[@]}" exec -T db pg_dump -U slotbook -Fc slotbook > "$backup_file"
test -s "$backup_file"
# Только новая проверочная БД; createdb завершится ошибкой, если имя уже занято.
restore_db="slotbook_restore_$(date -u +%Y%m%d%H%M%S)"
"${compose[@]}" exec -T db createdb -U slotbook "$restore_db"
"${compose[@]}" exec -T db pg_restore -U slotbook --exit-on-error -d "$restore_db" < "$backup_file"
"${compose[@]}" exec -T db psql -U slotbook -d "$restore_db" -c 'SELECT * FROM alembic_version; SELECT count(*) FROM bookings;'
# После проверки удалите только указанную проверочную БД.
"${compose[@]}" exec -T db dropdb -U slotbook "$restore_db"
)
```

Не восстанавливайте дамп поверх рабочей БД вслепую. При реальном восстановлении
сначала остановите записи, поднимите отдельную БД из копии, проверьте схему/данные,
затем переключите URL подключения и пересоздайте API. Смена DB URL требует
перезапуска, а готовность проверяется по `/health/ready`.

## Обновление и откат

Сохраните SHA прежнего приложения и дамп до изменения схемы. `migrate` выполняется
до API. При ошибке миграции не запускайте новый API вручную и не переписывайте
применённые ревизии. Если схема совместима со старым кодом, можно вернуть прежний
образ; readiness требует точного совпадения migration heads, поэтому откат только
кода после новой миграции может не пройти. Восстановление данных выполняйте отдельно
по проверенной копии. Автоматический downgrade рабочей БД не предусмотрен.

## Ограничения MVP

Нет регистрации, восстановления пароля, email-уведомлений и восстановления утраченной
manage-ссылки. При потере ответа на POST запись может быть сохранена; idempotency key
не реализован. Rate limit Nginx локален для экземпляра proxy. Сервер с HTTPS,
планировщик копий и внешнее хранилище копий настраиваются отдельно. Полный прогон
проверяет известные сценарии, но не является гарантией отсутствия ошибок.
