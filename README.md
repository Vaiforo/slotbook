Сервис записи на консультации: публичная страница специалиста, календарь
и доступное время из настоящего PostgreSQL. Все даты показываются в часовом
поясе специалиста. Выбранное время видно рядом с расписанием.

В интерфейсе доступны выбор времени, запись по имени и email, подтверждение
с секретной ссылкой и отмена встречи до её начала. В кабинете специалиста доступны вход, список записей и управление расписанием.

## Стек

- Python 3.14, FastAPI, Pydantic, SQLAlchemy 2, psycopg 3, Alembic.
- PostgreSQL 18, Docker Compose.
- React 19, TypeScript strict, Vite, React Router, TanStack Query.
- Tailwind CSS 4, компоненты по схеме shadcn/ui на Radix, Lucide.
- React Hook Form и Zod для доступной валидации формы записи.
- Temporal для корректных границ календарного дня в IANA timezone.
- uv/uv.lock и npm/package-lock.json для воспроизводимой установки.

## Запуск

Требуются Node.js 24 LTS, npm, [uv](https://docs.astral.sh/uv/getting-started/installation/),
GNU Make и Docker Compose. uv установит Python 3.14 при необходимости.
Все команды ниже выполняются из корня проекта.

```bash
make install
# Необязательно: локальные значения уже заданы по умолчанию.
cp .env.example .env
make db-up
make migrate
make seed-specialists
```

Затем в двух отдельных терминалах:

```bash
make backend
```

```bash
make frontend
```

Откройте [каталог](http://127.0.0.1:5173/). Публичные страницы доступны без входа.
Для записи выберите время и войдите или зарегистрируйтесь с ролью «Клиент».
После входа выбранное время проверяется повторно. Контакты берутся из аккаунта.
Кабинет `/dashboard` показывает обзор; `/dashboard/bookings` — собственные записи
клиента или входящие записи специалиста. Отмена доступна до начала встречи.

Специалист регистрируется отдельно, заполняет публичный профиль, услуги и смены
в кабинете и публикует страницу. Черновики в каталог не попадают.
Время кабинета клиента показывается в его часовом поясе, расписание — в часовом
поясе специалиста. Исторические секретные ссылки управления продолжают работать.

## Настройки

Backend и Vite читают корневой `.env`; переменные процесса имеют приоритет.
После изменения настроек перезапустите серверы.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `SLOTBOOK_APP_NAME` | `SlotBook` | Имя API |
| `SLOTBOOK_ENVIRONMENT` | `development` | development / test / production |
| `SLOTBOOK_LOG_LEVEL` | `INFO` | Уровень JSON-логов |
| `SLOTBOOK_DATABASE_URL` | Локальный URL из `.env.example` | SQLAlchemy URL с `postgresql+psycopg` |
| `POSTGRES_PASSWORD` | `slotbook_local_only` | Пароль локальной БД |
| `POSTGRES_PORT` | `5432` | Порт PostgreSQL на 127.0.0.1 |
| `SLOTBOOK_PUBLIC_ORIGIN` | `http://127.0.0.1:5173` | Точный browser origin без завершающего слеша; production требует HTTPS |
| `API_PROXY_TARGET` | `http://127.0.0.1:8000` | Серверный адрес dev proxy |

Пароль по умолчанию предназначен только для локальной разработки. При смене
пароля или порта измените также `SLOTBOOK_DATABASE_URL`. Изменение env не меняет
пароль уже инициализированного PostgreSQL volume. Переменные `VITE_*` публичны;
секреты в них хранить нельзя. Для приложения они не требуются.

Makefile размещает кэши uv/npm и управляемый Python в игнорируемой `.cache/`.
Backend environment находится в `backend/.venv/`. `.env`, окружения, кэши и
результаты сборки исключены из Git.

## База данных

Compose запускает PostgreSQL 18 с healthcheck. Порт опубликован только на
127.0.0.1, volume `postgres_data` смонтирован в `/var/lib/postgresql`.
`make migrate` применяет Alembic к текущей БД, `make seed-specialists` явно добавляет
синтетические демонстрационные данные.

Основные таблицы: users, sessions, specialists, slots, bookings.
Дополнительно: outbox_events, notification_deliveries и ai_usage. Ограничения БД запрещают
пересекающиеся слоты одного специалиста (включая закрытые), интервалы не по
30 минут и две confirmed-записи на один слот. Соседние интервалы допустимы.
Отменённые записи сохраняются. Моменты времени хранятся как timestamptz,
IANA timezone — отдельной строкой.

`make seed-specialists` создаёт 10 вымышленных профилей: 3 медицина, 3 сантехника,
2 юриспруденция и 2 доставка. Свободные интервалы создаются на следующие 14 дней;
бронирования не создаются. Повторный запуск не дублирует объекты, не перезаписывает
профили и не открывает закрытые интервалы. Вход в синтетические аккаунты отключён.
Старый демопользователь удаляется миграцией `e1420a03`; на время миграции остановите
обработчики уведомлений. Автоматического присоединения исторических броней по email нет.

## API

- [Swagger UI](http://127.0.0.1:8000/docs).
- `GET /health/live` — жизнь процесса, без проверки готовности БД.
- `GET /health/ready` — доступна БД и совпадает версия миграций, иначе 503.
- `GET /api/v1/specialists/{slug}` — публичный профиль без приватных полей.
- `GET /api/v1/specialists/{slug}/slots?from=…&to=…` — будущие свободные open-слоты.
- `POST /api/v1/bookings` — создать запись; manage token выдаётся один раз после commit.
- `GET /api/v1/bookings/{booking_id}` — прочитать свою запись по Bearer token.
- `POST /api/v1/bookings/{booking_id}/cancel` — отменить её до начала встречи.

`from`/`to` обязательны, ISO 8601 с offset или `Z`. Диапазон `[from, to)` по
началу слота — не больше 31 дня. `limit` — 1–100, `offset` — 0–10000.
При использовании curl применяйте `--get --data-urlencode`, чтобы сохранить
`+` в часовом поясе. Неизвестный специалист — 404, неверные параметры — 422.

Все ответы API содержат `X-Request-ID`. Ошибка имеет вид
`{error: {code, message, request_id}}`. JSON-логи содержат шаблон маршрута,
статус и длительность, без query strings, контактов и токенов.
[Подробный HTTP-контракт](docs/api-contract.md).

Чтение профиля и списка свободного времени (даты замените на нужные):

```bash
curl --fail http://127.0.0.1:8000/api/v1/specialists/anna-belova
curl --fail --get http://127.0.0.1:8000/api/v1/specialists/anna-belova/slots \
  --data-urlencode 'from=2030-01-02T00:00:00+06:00' \
  --data-urlencode 'to=2030-01-03T00:00:00+06:00'
```

Запись → приватное чтение → отмена → проверка свободного времени на текущих
синтетических данных: `python3 scripts/booking-journey.py --book-and-cancel`.
Команда изменяет локальную демо-БД, оставляя отменённую запись; токен не выводится.
Подготовка и пользовательский сценарий описаны в [сценарии](docs/getting-started.md).

Pydantic/OpenAPI — источник TypeScript-типов:

```bash
make api-generate
make api-check
```

Обе команды работают без БД. Проверка обнаруживает расхождение OpenAPI и
сгенерированных типов без перезаписи файлов. HTTP-клиент поддерживает
AbortSignal, same-origin credentials и типизированные ошибки. React Query
повторяет запрос сети/5xx не более одного раза; 4xx не повторяются.
Автоматические повторы mutations отключены.

## Проверки

```bash
make check
make db-test
PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium make smoke
```

`make check` выполняет api-check, Ruff/format, mypy, backend unit/smoke tests,
ESLint, Vitest, TypeScript strict и frontend build. Без `SLOTBOOK_TEST_ADMIN_URL`
интеграционные backend-тесты пропускаются; их отдельно запускает `make db-test`.

Для браузерных проверок сначала выполните `make db-up` и остановите dev-серверы.
`make smoke` сам создаёт случайную БД `slotbook_browser_<uuid>`, применяет миграции,
запускает seed, FastAPI и Vite. После штатной остановки тестовая БД удаляется.
Рабочие данные не изменяются. Проверяются реальные профиль/слоты, выбор времени,
смена даты, клавиатура и диалог, loading/empty/error/retry, неизвестные страницы
и размеры 390/768/1440 px. Также проверяются запись → отмена → повторная запись,
конфликт с другим клиентом, сохранённая ссылка, очистка fragment, отсутствие
секрета в хранилищах/URL запросов/консоли и восстановление после перезагрузки.
Vitest проверяет форму, 409/422/сетевые ошибки и блокировку повторной отправки.
Сетевые ошибки и задержки вводятся только в тестах;
успешные ответы приходят из настоящего API. Скриншоты — в `frontend/test-results/`.

Если системного Chromium нет, установите браузер Playwright:

```bash
cd frontend
npx playwright install chromium
cd ..
make smoke
```

`make db-test` также создаёт собственную БД `slotbook_test_<uuid>`, проверяет
upgrade → downgrade → upgrade, ограничения, seed, read API и удаляет её.
Адрес сервера можно переопределить через `SLOTBOOK_TEST_ADMIN_URL`;
нужны PostgreSQL 18 и право CREATEDB. Пользовательская БД не откатывается.

## Сборка и ограничения

`frontend/dist/` содержит статическую сборку. Для production требуется reverse
proxy с маршрутизацией `/api`, `/health`, `/docs`, `/openapi.json` в FastAPI
и SPA fallback для `/s/:slug`, `/manage/:id`, `/login` и `/dashboard/*`. Production proxy, контейнеры и CI включены в проект.
HTTPS и публичный деплой требуют отдельной настройки сервера.

Просмотр доступности не гарантирует последующее бронирование: API создания
повторно проверяет слот в транзакции после блокировки строки. Время берётся из
PostgreSQL после ожидания блокировки. Повторная отмена старой записи не затрагивает
новую запись на том же слоте. Исходный manage token хранится только у клиента;
сервер хранит SHA-256-хеш. При потере ответа после commit повтор POST не
гарантирует восстановление результата и может вернуть 409. Интерфейс явно
сообщает о неопределённом результате при потере ответа; восстановление
утраченного токена пока не поддерживается.


Тесты бронирования в `make db-test` включают 20 одновременных TCP HTTP-запросов
с барьером старта и 20 независимыми соединениями PostgreSQL: один 201,
остальные 409, в БД одна confirmed-запись. Также проверяются чтение/отмена по
токену, ожидание блокировки до начала встречи, идемпотентная отмена, rollback
после flush и отсутствие обхода авторизации через cookie/query. Проверки
используют только одноразовые тестовые БД, не рабочие данные.

## Доступ владельца через API

`POST /api/v1/auth/login` принимает email/password и требует заголовок Origin,
равный `SLOTBOOK_PUBLIC_ORIGIN`. Возвращает HttpOnly/SameSite=Lax cookie `session`
на 12 часов. Secure включён для HTTPS; обычный HTTP допускается только для
loopback в development/test. Production-конфигурация с HTTP отклоняется.

`GET /api/v1/auth/me` возвращает id/email/CSRF token и собственный профиль специалиста. Для `POST /auth/logout`,
`POST /slots` и `PATCH /slots/{id}` нужны cookie, Origin и X-CSRF-Token.
`GET /api/v1/me/specialist/bookings` поддерживает from/to/status/limit/offset и возвращает
только записи текущего владельца. Чужие слоты нельзя изменять (404).

Закрытие занятого слота возвращает 409, не отменяя запись клиента. Закрытие и
бронирование сериализуются блокировкой строки слота. Создание/обновление слотов
проверяет время PostgreSQL; пересечения дополнительно запрещены ограничением БД.
Аутентификация и изменения используют одну транзакцию; ответ отправляется после
commit. Нет регистрации, восстановления пароля и rate limiting.

## Кабинет специалиста

Откройте `/register` и создайте свой аккаунт специалиста, затем войдите в кабинет.
В production секретная cookie требует HTTPS; локальный Origin должен совпадать
с `SLOTBOOK_PUBLIC_ORIGIN`, включая порт.

`/dashboard` показывает записи с фильтрами дат (до 31 дня) и статуса, по 20
записей на страницу. Фильтры сохраняются в URL. `/dashboard/schedule` показывает
неделю и слоты выбранного дня: свободные, закрытые и занятые. Можно опубликовать
30-минутный слот, закрыть его с подтверждением или открыть снова. Занятые и
прошедшие слоты недоступны для изменения; окончательное решение принимает API.
Дата и время в кабинете всегда указаны в часовом поясе специалиста.
Неоднозначное/несуществующее время при переводе часов отклоняется с объяснением.

`GET /api/v1/me/slots` возвращает собственные слоты, включая закрытые и прошедшие,
с признаком `has_booking`, без контактов клиентов. Профиль берётся из текущей
сессии, без пользовательского ввода specialist_id. При отсутствии профиля
показывается сообщение о необходимости его настройки.

При 401 приватные запросы отменяются, кэш очищается, интерфейс возвращает на
вход с сохранением выбранной страницы и фильтров. Выход отзывает сессию на сервере
и очищает приватный кэш. Ключи запросов содержат ID владельца; при смене аккаунта
данные прежнего владельца не отображаются. Пароль и CSRF не сохраняются в браузерных
хранилищах. Клиентская проверка сессии дополняет серверную проверку доступа.

Браузерные тесты используют двух синтетических владельцев только в одноразовой
тестовой БД. Проверяются публикация → клиентская запись → список владельца,
закрытие/открытие слота, конфликт времени, фильтры, выход/смена владельца,
401 после чтения/изменения, сетевые ошибки и размеры 390/768/1440 px.

При фоновой проверке сессии кабинет временно скрыт и недоступен для действий,
но введённое время и состояние отправки сохраняются. После успешной проверки
того же аккаунта фокус возвращается в прежнее поле; приватные списки обновляются
после проверки сессии. При смене аккаунта используется отдельное состояние кабинета.
Переход между страницами переводит фокус в основное содержимое; смена фильтров
и даты оставляет фокус на используемом элементе. Диалоги прокручиваются на низких
экранах, чтобы кнопки подтверждения и отказа оставались доступными.

Дополнительные браузерные проверки используют отдельные cookie-контексты владельца
и клиента, включая часовой пояс America/Los_Angeles. Покрыты запись перед закрытием
слота, отмена с освобождением времени, повторная проверка сессии во время ввода и
отправки, клавиатурные переходы, неверный период и маленькая высота экрана.
Каждый полный запуск создаёт новую одноразовую PostgreSQL-базу; повторный запуск
не зависит от данных предыдущего. Скриншоты остаются в игнорируемом test-results.

## Docker и автоматические проверки

Требования: Docker Engine с Compose v2; для разработки — Node.js 24 LTS,
Python 3.14 и uv 0.12.23. В контейнере frontend остаются только Nginx и статика.

```bash
cp deploy/.env.example .env.production
# Укажите пароль, совпадающий URL БД (host db), публичный HTTPS origin и IMAGE_TAG.
docker compose --env-file .env.production -f compose.production.yaml build
docker compose --env-file .env.production -f compose.production.yaml up -d --wait
```

`IMAGE_TAG` рекомендуется задавать SHA коммита. Пароль в URL должен быть URL-encoded,
если содержит специальные символы. Конфигурация и секреты передаются только backend
во время запуска; `.env` исключены из контекстов Docker. Seed не запускается автоматически.

Nginx слушает `127.0.0.1:8080` на хосте. Публичный сервер должен завершать TLS
перед этим портом и сохранять Host. Укажите его точный HTTPS origin без `/` в конце.
Сертификаты и публичный сервер не создаются этими командами. Cookie в production
всегда Secure; HTTP-проверка контейнеров не предназначена для входа пользователя.
Порты API и PostgreSQL не публикуются. Данные хранятся в volume `postgres_data`;
`down` сохраняет их, `down -v` удаляет. Перед обновлениями делайте резервную копию БД.

Одноразовый `migrate` применяет Alembic до старта API. `/health/live` проверяет процесс,
`/health/ready` — доступность БД и точное совпадение миграций с кодом; при сбое
возвращает 503 без деталей подключения. Nginx проксирует `/api`, `/health`, `/docs`,
`/openapi.json`; неизвестные API-маршруты возвращают JSON 404. Для React работает
SPA fallback. Access logs отключены, чтобы не сохранять секретные ссылки.
Базовый лимит Nginx для входа и записи возвращает JSON 429 с Retry-After.
За внешним proxy лимит применяется к адресу proxy; настройка доверенных адресов
и восстановления IP зависит от конкретного сервера.

GitHub Actions запускает `make check` (включая PostgreSQL и контроль OpenAPI/types),
Playwright и сборку обоих образов с запуском отдельного Compose-проекта.
Для локальной проверки контейнеров после `make install` и установки Chromium:

```bash
bash scripts/check-production.sh
```

Скрипт создаёт одноразовый volume, проверяет прямые браузерные переходы, маршрутизацию,
готовность при неверной/отсутствующей миграции и остановленной БД, затем удаляет
только свой проект. Нужен свободный порт 18080 (либо `SLOTBOOK_CHECK_PORT`).
В среде с HTTPS proxy Docker build поддерживает необязательный BuildKit secret
`proxy_ca`; сертификат не включается в образ. Branch protection на GitHub
настраивается отдельно; наличие workflow само по себе не запрещает merge.

Nginx обновляет адрес API через DNS Docker: после пересоздания контейнера
проксирование восстанавливается без перезапуска Nginx. Запросы к API не
пересылаются автоматически повторно при сбое upstream. Ошибки Nginx для слишком
большого тела (413), лимита запросов (429) и недоступного API (503) имеют JSON-формат
`error` с `request_id`, заголовок `X-Request-ID` и запрет кэширования. Ошибки,
возвращённые самим FastAPI, сохраняют исходный статус и тело.

Контейнерная проверка принудительно меняет адрес API и проверяет восстановление
связи. Также проверяется возобновление запросов после остановки и запуска PostgreSQL
без перезапуска API. Эти проверки используют только одноразовую тестовую БД.

## Общие лимиты запросов

Production использует Redis 8.2 внутри Compose без опубликованного порта. Все
процессы API используют одно окно: 10 POST на `/api/v1/auth/login` и 20 POST на
`/api/v1/bookings` за 60 секунд на IP, включая неверные запросы. Атомарный Lua-script
увеличивает счётчик и задаёт TTL. Лимит возвращает JSON 429 `rate_limited` и
`Retry-After` в секундах до конца окна; автоматических повторов POST нет.

При недоступности Redis обе операции отклоняются до записи в PostgreSQL:
503 `rate_limit_unavailable`, `Retry-After: 5`. Чтение расписания, управление
существующей записью и проверка готовности БД не зависят от Redis. Доступность
слотов не кэшируется; PostgreSQL по-прежнему обеспечивает запрет двойной записи.

`SLOTBOOK_REDIS_URL` обязателен в production. В development лимитер выключен,
пока URL не задан явно; `make db-up` запускает локальный Redis на 127.0.0.1:6379.
Порог задают `SLOTBOOK_LOGIN_LIMIT`, `SLOTBOOK_BOOKING_LIMIT` и
`SLOTBOOK_RATE_WINDOW_SECONDS`. Все экземпляры должны иметь одинаковые настройки
и `SLOTBOOK_RATE_PREFIX` (по умолчанию `slotbook:rate:v1`). Ключи содержат SHA-256
адреса клиента, без email/паролей/контактов. Это не анонимизация IP.

Nginx перезаписывает X-Forwarded-For адресом соединения. Контейнер API доверяет
forwarded-заголовкам только в закрытой Docker-сети; не публикуйте его порт и не
подключайте к этой сети недоверенные сервисы. При прямом dev-запуске Uvicorn
использует стандартный список доверенных proxy. За внешним TLS proxy пользователи
могут разделять один IP; настройка real IP требует точного списка доверенных proxy.
Дополнительные ограничения Nginx остаются действовать.

Redis использует максимум 64 MB, `noeviction` и не сохраняет счётчики на диск.
После перезапуска окно начинается заново; при заполнении памяти запись блокируется
как при недоступности Redis. Лимит фиксированного окна допускает всплеск на его
границе и не заменяет защиту от распределённых атак.

Для интеграционных проверок лимитера задайте
`SLOTBOOK_TEST_REDIS_URL=redis://127.0.0.1:6379/0` вместе с test admin URL при
`make check`. Тесты используют случайные префиксы с TTL, не выполняют FLUSHDB.
Проверяется общий бюджет двух независимых процессов API и отказ Redis.

## Уведомления

Запись и отмена сохраняют события в PostgreSQL, dispatcher передаёт их через
RabbitMQ в Celery worker. [Устройство, запуск, статусы и повторы](docs/notifications.md).
Production требует `RABBITMQ_PASSWORD`; по умолчанию используется локальный HTTP sink.
Для внешней доставки нужен совместимый HTTPS gateway и его credentials.

## Подбор времени по описанию

Кнопка «Подобрать по описанию» принимает пожелание вроде «завтра с 15:00 до 18:00».
Backend проверяет структуру ответа модели и выбирает реальные свободные слоты.
Пользователь видит интерпретацию даты/времени, выбирает слот и подтверждает запись
через обычную форму. Без провайдера, при ошибке или исчерпании бюджета доступен календарь.

[Настройка, ограничения расходов и eval](docs/ai-search.md). Модель по умолчанию
отключена. Нужны ключ, model ID, Redis и сетевой доступ к HTTPS API провайдера.
`make ai-eval` проверяет 25 локальных contract-fixtures; они не измеряют accuracy LLM.
Live-интеграция и качество реальной модели пока не проверены.
